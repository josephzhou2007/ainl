最大的一个 token 杠杆：media_resolution

依据 docs/research/handwriting-ocr-options-2026-09.md:16-25： Gemini 3.x 按 media_resolution 对图片计费 —— low = 280 image token，medium = 560，high（默认）= 1120。

代码从来没有设置过 media_resolution，也从来没有压缩过照片， 所以每一页都在按默认的 1120 付费。在约 1,300 的输入 token 里，图片本身就占了 1120 —— 提示词（573 + 238 字符）只是零头。这是目前唯一能明显砍掉输入 token 的开关。

诚实的警告：那份 ~95% 的准确率是在默认的 high 分辨率下测出来的。 调到 medium 或 low 没有被测过。手写数学对细节敏感，如果降分辨率导致读错率上升， 多出来的重拍、打字修正和升级到 claude-sonnet-5（贵 9 倍）的次数， 很可能比省下的 token 更贵。要动这个开关，应该先在自己的答题纸上做一次 A/B 实测。

06Gemini 对象的生命周期

没有常驻客户端、没有连接池、没有 SDK 对象。一次调用从建到灭，全在一个函数栈里。

1
读 keygemini.py:28，在 __init__ 里读环境变量 GEMINI_API_KEY（gemini.py:15）。 不是在 import 时读 —— 没配 key 也不影响其他功能启动。
2
每次调用现造 providerpipeline._load pipeline.py:184-191 → registry.get registry.py:25。 provider 实例不复用。
3
一次 HTTP POSTbase.http_post base.py:88-95，直接调 httpx.post，超时 60 秒，无重试。
4
立刻结束httpx.post 是模块级便捷函数，它内部开一个一次性 client，返回时就关掉。 没有持久 client、没有连接池、没有 SDK 对象、没有 close()。 transcribe_with_consensus 返回后 provider 对象被垃圾回收。
5
没有真实计量代码从不读取 Gemini 返回里的 usageMetadata， 所以 result.cost_usd 是一个按次估算的固定值，不是真实账单。 要知道实际花了多少，得去 Google 控制台看，或者改代码把 usageMetadata 记下来。

结论

  • 要降 LLM 成本，只需要盯 mathinput/ 这 1,322 行，别的地方优化不产生任何节省。
  • 当前单价已经很低（$0.35/1000 页，一学期约一两角）；最大的浪费是图片按默认 high = 1120 image token 计费，且照片从不缩放。
  • 降 media_resolution 是唯一明确的杠杆，但准确率只在 high 下测过，先做 A/B 再动。
  • 想要真实数字而不是估算，先把 Gemini 返回的 usageMetadata 记录下来。
页面上的行数、行号、常量与端点均取自仓库代码；token 数、耗时与准确率取自 docs/research/gemini-vs-pix2text-2026-09-19.md 与 docs/research/handwriting-ocr-options-2026-09.md。 标注 估算 的数字为推算而非实测。
