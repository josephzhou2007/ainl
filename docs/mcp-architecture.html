MCP 服务器到底是什么？
——从你这台机器上的六个说起

MCP 服务器不是一种特殊的程序。它就是 Claude 启动的一个普通进程，通过一根管道，用一行一条的文本协议跟 Claude 说话。

配置文件：%APPDATA%\Claude\claude_desktop_config.json　·　本机共六个服务器　·　案发时间 2026-09-19 21:01:39

打开那个配置文件，你会发现每一个「服务器」条目里写的，无非是一条命令行：一个可执行文件，加一串参数。Claude 做的事情，和你在 PowerShell 里敲下这行命令没有本质区别——它 spawn 出一个子进程，然后和它讲话。

所以「MCP 服务器挂了」这句话，在操作系统眼里永远是同一件事：那个子进程没了。至于它背后真正干活的东西有没有一起没，那是另一个问题——本文后半段那次事故，答案恰好是「大多没有」。

01六个服务器，其实只有四种形状

把六条命令行摊开看，node.exe 出现了五次。但 node.exe 只告诉你「跑这段代码的解释器是 Node」，完全没告诉你这个程序是什么。真正区分它们的，是那个 node 进程里的代码把活儿交给了谁：

  • 形状 1 · 纯 node 服务器　活儿就在这个 node 进程里干完。jshook、reqable-mcp。
  • 形状 2 · node 代理 → 另一门语言的子进程　node 只是转发员，真正的引擎是它 spawn 出来的 Python。scrapling。
  • 形状 3 · node 代理 → HTTP → 正在运行的 GUI 程序　anything-analyzer → 127.0.0.1:23816。
  • 形状 4 · node 桥 → HTTP → Java 程序里的插件　burpsuite → 127.0.0.1:9876 → Burp Suite 的 “MCP Full Control” 扩展。
  • 例外 · 根本没有 node　ocr-pdf 的命令是 wsl.exe，它跨进了 WSL 这个独立的 Linux 内核。

02两个代理，为什么要多这一层

你机器上有三个 node 程序，它们自己不提供任何工具，只是中间人。为什么要写它们？各自的源码头部写得很清楚。

C:\\Users\\you\Tools\mcp-schema-fix-proxy.js　124 行

它开头就 const { spawn } = require('child_process')——一上来就暴露了身份：它要生一个孩子。

问题出在类型描述上。Python 那边的 Pydantic / FastMCP 把「可选参数 Optional[X]」写成：

{"anyOf": [{"type": "X"}, {"type": "null"}], "default": null}

而 Claude 的 schema 转换层会把 anyOf 丢掉，字段就只剩下 {"default": null}——既看不出类型，又像是必填，于是调用一律失败。这个代理透明中继 stdio，只在 tools/list 的响应经过时动手，把 anyOf 展平成单一 type。其余所有消息原样放行。

C:\\Users\\you\Tools\mcp-resilient-proxy.js　205 行

它替代了 mcp-remote，解决的是一个启动顺序问题：后端是个 GUI 应用，如果它没开，tools/list 就会失败；tools/list 一失败，整个 MCP 服务器就起不来，Claude 面板上挂一个红叉。

策略是缓存：tools/list 成功一次就把结果写到磁盘；后端离线时用缓存清单应答，服务器照常启动（面板不报红）；只有真的发起 tools/call 时，才返回一句清楚的「请先启动后端」。

D:\code\local\projects\reverse-skill\burp-mcp-full\mcp-bridge.js　408 行

头部自述：把自定义的 HTTP API（端口 9876）桥接成标准的 MCP JSON-RPC 2.0 stdio 协议。它从 ~/.burp-mcp-token 或环境变量 $BURP_MCP_TOKEN 读一个令牌，以 Authorization: Bearer 发出去；GET /tools 取工具清单，POST / 发起调用。离线缓存的思路和上面那个代理一模一样。另一端的 Burp 插件是同一个仓库里的 Java 扩展（gradle 构建，源码在 src/）。

顺带记住一条规矩：这三个程序的日志全都写 stderr，一行都不写 stdout。因为 stdout 是协议专用车道——你往里多打一个 console.log，对面就会读到一行不是 JSON 的垃圾，整条连接当场报废。

04stdio 传输：两个进程之间的一根管子

Claude 启动服务器进程的时候，会把它的 stdin 和 stdout 接到管道上（这正是 spawn 能做的事），然后双方在这根管子上讲 JSON-RPC 2.0：一行一条消息，换行符就是分隔符。

Claude 往服务器的 stdin 写一行：

{"jsonrpc":"2.0","id":1,"method":"tools/list"}

服务器往自己的 stdout 回一行：

{"jsonrpc":"2.0","id":1,"result":{"tools":[
  {"name":"fetch","description":"抓取一个网页","inputSchema":{"type":"object",
   "properties":{"url":{"type":"string"},"timeout":{"type":"number"}},
   "required":["url"]}}
]}}

id 用来把回答和提问配对（可以有好几条同时在飞）；真正调用工具时，method 换成 tools/call。第 02 节那个 schema 代理，改的就是这个 inputSchema 里的东西。

关键一点：这不是网络连接。没有 IP，没有端口，没有 socket，别的程序连不进来。它是内核里的一个缓冲区，两端各握着一个文件描述符。只要有一端的进程消失，管子立刻失效——另一端读到 EOF，或者写入时收到「管道中断」。

所以日志里那句 Server transport closed unexpectedly, this is likely due to the process exiting early，翻译过来就是：我这头还在，管子那头的进程没了。

052026-09-19 21:01:39：一条命令带走五个

当时的目的完全正当：清理泄漏的 Playwright driver 进程。执行的是这一行——

Get-Process node -ErrorAction SilentlyContinue | Stop-Process -Force

然后，%LOCALAPPDATA%\Claude\logs\mcp.log 在 96 毫秒内连着记下五行：

02:01:39.421Z  [scrapling]          Server transport closed
02:01:39.442Z  [burpsuite]          Server transport closed
02:01:39.465Z  [reqable-mcp]        Server transport closed
02:01:39.486Z  [anything-analyzer]  Server transport closed
02:01:39.517Z  [jshook]             Server transport closed

（日志用 UTC，02:01:39Z 就是本地 21:01:39。）每条后面都跟着同一句：Server transport closed unexpectedly, this is likely due to the process exiting early.

看名单：不多不少，正好是那五个「直系子进程是 node.exe」的服务器。ocr-pdf 不在里面。

因为 Claude 为 ocr-pdf spawn 出来的那个进程叫 wsl.exe，不叫 node.exe。Get-Process node 按映像名筛选，它没被匹配到，那根管子一点事都没有——更不用说管子那头的 python3，它根本活在另一个 Linux 内核里。

怎么确认「确实是被集体重启的」

正常情况下，各个 node 进程是在不同时刻陆续启动的，启动时间应该散落在几小时甚至几天里。而当时 13 个 node 进程的启动时间全部落在 21:03:18–21:03:44 这 26 秒窗口内。启动时间高度一致，本身就是「它们刚刚被一起重新拉起来」的证据。

06为什么 node.exe 是个糟糕的筛选条件

这是整件事唯一真正的教训，值得单独说清楚：

映像名（node.exe、python.exe、java.exe）说的是「用哪个解释器跑」，不是「这是什么程序」。

就像你不会因为要删掉一份 Word 文档，就把所有 WINWORD.EXE 全关掉。程序真正的身份写在命令行里：Win32_Process.CommandLine。

所以那次清理本该写成这样——先筛出真正想杀的那些，看一眼确认，再动手：

# 1) 先看清楚要杀谁（永远先跑这一步）
Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
  Select-Object ProcessId, CreationDate, CommandLine |
  Format-List

# 2) 只对命令行匹配的那些下手
Get-CimInstance Win32_Process -Filter "Name = 'node.exe'" |
  Where-Object { $_.CommandLine -like '*playwright*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }

注意 Get-Process 返回的对象上没有 CommandLine 这个属性，所以必须换成 Get-CimInstance Win32_Process。顺手把 CreationDate 也打出来：启动时间是判断「这是不是泄漏出来的野进程」的好线索。

还有一条更根本的：修漏比扫地重要。Playwright driver 会泄漏，说明某段代码没有关掉它启动的浏览器。定期拿扫把横扫一遍，只是把问题从「泄漏」变成「泄漏 ＋ 每隔一阵误伤一批无辜进程」。去找那个没被调用的 close()。

07两种边界，记住它们的区别

stdio 管道本地 HTTP 端口
本机例子六个服务器的第一跳，全都是它:23816 Analyzer、:9876 Burp
是谁的进程必须是 Claude 的子进程谁都行，独立运行的程序
Claude 重启之后管道失效，服务器必须重新 spawn后端毫发无损，重连即可
需要认证吗不需要——管子只有两头，别人进不来需要。端口是开放的，所以 Burp 那边才要 Authorization: Bearer 令牌
前置条件命令能跑起来就行那个应用必须先开着（这正是 resilient proxy 要做离线缓存的原因）

08一句话总结

MCP 服务器是一个进程。它的身份写在命令行里，不写在映像名里。它和 Claude 之间是一根管子，管子断了不等于它背后的东西死了。而 ocr-pdf 之所以能在那次扫射里安然无恙，仅仅因为它的第一跳叫 wsl.exe——操作系统就是这么字面、这么不讲情面。
