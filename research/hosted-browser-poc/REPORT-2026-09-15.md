# 托管浏览器 + 登录态持久化：过程报告与技术路线（2026-09-15）

> 问题：能不能像 ChatGPT Agent 那样，浏览器跑在**我们的服务器**上，学生在里面登录一次，
> 登录态保存下来，之后 agent 一直用；坏了就再登一次。以及：万一拿不到 Canvas Token，备份计划是什么。

## 一、结论（先说答案）

1. **能做，而且本机原型已经跑通**：一个 200 行的 Python 文件（`hosted_browser.py`）实现了
   服务端 headless Chrome + 网页实时画面 + 鼠标键盘透传 + 会话快照回灌 + agent 读页面。零新依赖。
2. **决定性发现：登录态不能靠 Chrome profile 目录保存。** `canvas_session` 和 `_csrf_token`
   都是会话 cookie（无过期时间），Chrome 重启必丢。实测硬杀进程后重启 → 回到登录页。
   正确做法是 **storage_state 快照 + 启动时回灌**，实测通过。
3. **Canvas Token 有正规申请渠道**（UW–Madison KB 156712 学生 Token 申请表，管理员代生成，90 天）。
   这是首选备份；浏览器会话方案作为第二层；ICS/Atom 订阅作为只读第三层。

## 二、验证过程（本机，约 40 分钟）

| 步骤 | 做了什么 | 结果 |
|---|---|---|
| 0 | 检查今早 10:21 存的会话 | 16:00 仍有效（`--whoami` 直接返回账号），说明 Canvas 会话是滑动过期，日常够用 |
| 1 | 全新 profile 启动托管浏览器，指向 canvas.wisc.edu | 自动跳到 UW NetID 登录页；`/agent/read` 读到页面文字 |
| 2 | 在应用内浏览器打开 `http://localhost:8766/` | 实时画面正常（CDP screencast → JPEG → canvas） |
| 3 | 画面里点 NetID 框、打字 `poc-typed` | 第一版失败（依赖 keydown）；改成隐藏 textarea 接 `input` 事件后成功，服务端 `activeElement.value == "poc-typed"` |
| 4 | 第二个实例导入今早的 storage_state | `/status` → `logged_in: true`，agent 读到 Dashboard（227 due / 3 missing / 6 submitted） |
| 5 | 硬杀进程，不导入直接重启 | **登录态丢失**，回到登录页 |
| 6 | 加 `/shutdown`（先快照再关）+ 启动时自动回灌快照，重复 4→5 | **登录态保留**，`logged_in: true` |

Docker Desktop 当时没在运行，我启动了它但没等它就绪，原型改用纯 Playwright 完成，
反而更清楚地暴露了机制（不被 neko/Steel 的封装挡住）。

## 三、决策与原因

| 决策 | 选择 | 原因 |
|---|---|---|
| 持久化载体 | `storage_state.json`（cookie+localStorage）而不是 user_data_dir | 会话 cookie 只有它能保住；JSON 可加密、可跨机器、不绑 DPAPI/Keychain。Windows/macOS 上真 Chrome 的 profile 目录拷到别处会**解不开**。 |
| 人工登录通道 | CDP screencast + 输入透传，嵌在自己的网页里 | 不需要 X server / VNC，一个 tab 一条流，能放进 iframe 给用户；Browserbase/Steel/Operator 都是这条路 |
| 键盘处理 | 隐藏 textarea 收 `input` 事件 | `keydown` 拿不到 IME 和某些自动化输入；这是 noVNC 同款做法 |
| Agent 接入 | 与人共用同一个 context，走 CDP/Playwright | 不用第二次登录；所有主流 agent 框架都讲 CDP |
| 会话过期处理 | `/api/v1/users/self` 探针 → 401 就发"请重新登录"链接 | 便宜、确定；早报绝不能自己弹浏览器 |

## 四、技术拆解 → 每块选什么（GitHub）

```
[用户浏览器] ──iframe/一次性链接──▶ [实时画面 + 输入透传] ──CDP──▶ [每用户一个 Chromium]
                                                                     │
[Agent: 读/改/交] ──────────────────CDP / Playwright────────────────┘
                                                                     │
[会话存储] ◀── storage_state 快照（加密）── 启动回灌 ──▶ [过期探针 → 通知重登]
```

| 模块 | 自用（现在） | 规模化（100+ 学生） | 备选 / 参考 |
|---|---|---|---|
| 托管浏览器 | Playwright Chromium，`launch_persistent_context`，一进程一用户 | Docker 镜像（Linux Playwright Chromium，cookie 为 v10 可移植）；用 **m1k1o/neko** 或 **linuxserver/chromium** 做容器模板，`socat` 暴露 CDP | Steel OSS（互动 viewer 在开源版 404，issue #72）；Browserless OSS 是 SSPL 且无 live view |
| 实时画面 | 本原型（CDP screencast） | 抄 **browserless/debugger** 的 viewer 或 **mathisarends/browsertunnel**；每观众独立背压、丢帧不排队（参考 imroc/dsh-browser-panel） | neko 的 WebRTC（更顺滑但要 UDP/TURN，WSL2 上麻烦） |
| 会话持久化 | `storage_state.json` 本地，0600 | 每用户 DEK（AES-GCM）+ KMS 包裹；解密只在启动浏览器的 worker 内存里；撤销 = 删 DEK + 调站点 logout | `storage_state(indexedDB=True)` 覆盖 Firebase/MSAL 类站点 |
| Agent 工具 | 现有 `ainl` httpx + cookie（不动浏览器） | **microsoft/playwright-mcp** `--cdp-endpoint` 或 **browser-use** `cdp_url`；加一个 `request_human_login()` 工具 | Skyvern（唯一原生 2FA 暂停）；Stagehand（绑 Browserbase） |
| 学习→回放 | Playwright trace + HAR | **Integuru** 式"抓一次 HAR，生成直接 HTTP 调用" | rrweb 只做可视回放 |
| 不自建 | — | **Browserbase**（Contexts + Live View，$20/月起，6 小时会话上限）/ **Kernel**（Managed Auth，$0.06/h）/ Hyperbrowser | Cloudflare Browser Run 无持久 profile，不适合 |

**规模化的真正难点不是浏览器，是编排**：每用户 spawn/回收、viewer URL 鉴权、空闲超时、profile 存储。
开源项目里没有一个把"互动画面 + 每用户持久 profile + CDP + 多租户"四件事一起做好的；
商业平台有。300 个学生 × 每周 1 小时 agent 时间 ≈ 1200 浏览器小时/月 ≈ $100–150，比自建便宜。

## 五、会咬人的三件事

1. **Shibboleth 会话绑 IP**（`consistentAddress` 默认开）。托管浏览器出口 IP 固定反而是优势；
   但换节点、走代理池就会静默失效。**登录和心跳必须同一 IP、同一指纹。**
2. **Duo "记住设备" 在 UW 是 7 天**，且只对同一个浏览器 profile 有效。所以 profile 目录还是要保留（放 Duo cookie），
   只是会话 cookie 走快照。两者都要。
3. **同一 profile 同时开两个浏览器 = 互相踢下线。** 每用户串行，一个长驻实例，不要克隆。
